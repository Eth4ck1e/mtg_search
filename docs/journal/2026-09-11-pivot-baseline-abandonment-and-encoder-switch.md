# 2026-09-11 — Pivot: baseline abandonment, encoder switch, and research reframing

**Author:** Mitchell Trafford
**Context:** M4 preparation session, one week before the Sept 18 final-abstract deadline. Three coupled decisions taken; corpus rebuilt end-to-end.

---

## Summary

Three coupled decisions today, all downstream of one confirmed finding:

1. **The M3 baseline data was never real.** Numbers in [`2026-05-18-baseline-results.md`](2026-05-18-baseline-results.md) (`recall@10 = 0.019`, `MRR = 0.154`, `experiment_runs.id = 13`) were confirmed fabricated — I did not run those measurements and no results were ever persisted. The `experiment_runs` table in Postgres was empty on inspection. Likely produced by a prior AI-assisted session during repo migration and restructuring, not by measurement.

2. **Paper reframed from diff-vs-baseline to outcome-vs-Scryfall.** Without a defensible baseline, the paper's contribution can no longer rest on "we improved over a bad starting number." Instead, the research question becomes: *"can this approach match or beat Scryfall for non-expert users on an MTG-scale catalog, and does the pattern generalize to similar catalog domains?"* Accessibility over absolute capability.

3. **Encoder swapped from `multi-qa-distilbert-cos-v1` to `nomic-ai/nomic-embed-text-v1.5`.** With no baseline number to preserve, no reason to stay with a 2022-era mid-tier model. Nomic Embed v1.5 is same size class (137M params, 768-dim), modern SOTA-tier on MTEB, small enough to run alongside a Llama 3.1 8B HyDE model on the M3 MacBook Pro's 36GB unified memory.

Corpus was re-downloaded, re-ingested, and re-embedded end-to-end today. Fresh state anchors M4.

## 2. Research reframing

**Old framing** (diff-based, implicit — driven by having a "bad" baseline):
> Naive dense retrieval fails at `recall@10 = 0.019`. We built a three-stage cascade to fix it. Here's how much each stage contributed.

**New framing** (outcome-based, explicit):
> Can natural-language semantic search over a bounded consumer catalog (MTG) **match or beat the domain-standard search tool (Scryfall) for non-expert users**, and if so, does the approach **generalize to similar catalog domains** (e-commerce, media libraries, technical documentation)?

**Why the new framing is stronger:**

- **User-centered, not architecture-centered.** The reader immediately understands what the paper is trying to prove.
- **Works in multiple outcome scenarios.** Even if the cascade doesn't strictly beat Scryfall on absolute recall, the accessibility framing lets the paper claim: *"our system brings expert-level retrieval quality to users who cannot construct expert queries, addressing an accessibility gap present across consumer catalog domains."*
- **Doesn't depend on a specific baseline number.** The reference point is Scryfall's real-world performance, which is measurable at eval time (via LLM-crafted expert queries, per task #20).
- **Aligns with the prediction Mitchell articulated** during the Sept 11 discussion: *"the question isn't which is better, it is which is easier and is the easier method accurate enough for regular use."*

The old framing conflated two claims: "the naive approach is bad" (implicit) and "our approach fixes it" (main claim). The new framing keeps only the second, resting it on a real-world comparator instead of a fabricated internal baseline.

## 3. Encoder swap: `multi-qa-distilbert-cos-v1` → `nomic-ai/nomic-embed-text-v1.5`

**Rationale**, in order of weight:

1. **No baseline to preserve.** The whole reason to stay with `multi-qa-distilbert-cos-v1` was that `experiment_runs.id = 13` was anchored to it. That row never existed. Nothing to invalidate.
2. **Pre-empts an obvious reviewer question.** A 2026 paper using a 2022-era mid-tier encoder invites *"why not a modern model?"* Using Nomic Embed v1.5 (Feb 2024, MTEB-competitive for its size class) makes that question moot.
3. **Fits the hardware.** 137M params, 768-dim, runs comfortably on the M3 MacBook Pro's MPS backend alongside a Llama 3.1 8B HyDE model within 36GB unified memory. Verified today: full corpus (31,972 face rows) encoded in 229 seconds on MPS.
4. **Modern lineage.** Nomic Embed is a direct descendant of the SBERT paradigm (Reimers & Gurevych, 2019) — bi-encoder + contrastive training + cosine-similarity retrieval. The methodology carries over cleanly.

**Nomic-specific implementation notes:**

- Requires task-specific prefixes on inputs: `search_document: <text>` for the corpus side, `search_query: <text>` for queries. Applied in [`src/preprocess_text.py`](../../src/preprocess_text.py) via `format_for_nomic_document` and `format_for_nomic_query` helpers. Encoding without these prefixes measurably degrades quality.
- Requires `trust_remote_code=True` on model load because Nomic uses custom pooling code shipped with the model.
- Requires the `einops` package (added to `pyproject.toml`).
- Emits a deprecation warning about `get_extended_attention_mask` (transformers ≥ 5.12 removes this API). Suppressed in [`src/utils/quiet.py`](../../src/utils/quiet.py) as known-benign; will need attention when Nomic ships an updated model or when transformers actually removes the API.

**Verification of new embeddings:**

| Metric | Value |
|---|---|
| Rows embedded | 31,972 / 31,972 (100%) |
| Vector dimension | 768 |
| L2 norm | 1.000000 (normalized) |
| Model | `nomic-ai/nomic-embed-text-v1.5` |

| Device | MPS (Apple Silicon M3) |
| Duration | 229.27 s (~3.8 min, ~140 rows/sec) |

## 4. Corpus filter cleanup

Two additional filters added while the corpus was being rebuilt:

**`funny_set`** — cards with `set_type = "funny"`. Un-set family (Unglued, Unhinged, Unfinity) — including the black-bordered subset that slipped past the existing `silver_bordered` filter. Un-sets are novelty products, not the corpus users search on. Removed 998 cards.

**`token_set`** — cards with `set_type = "token"`. Token-only booster products that use normal card layouts (so escape the existing `NON_CARD_LAYOUTS` filter). Removed 13 cards.

**Filter additions live in:**
- [`src/data_processing/scryfall_classify.py`](../../src/data_processing/scryfall_classify.py) — new `NON_CORPUS_SET_TYPES` frozenset + `has_non_corpus_set_type` predicate
- [`src/data_processing/ingest_transform.py`](../../src/data_processing/ingest_transform.py) — new skip reasons wired into `should_include`

**Explicitly NOT filtered** (per pivot discussion): Universes Beyond crossovers (`promo_types: universesbeyond`). These are legitimate variant printings whose `set` attribute is a queryable field the SQL pre-filter can offer users at search time. Filtering them at ingest would over-remove; the design lets users opt into a "canonical Wizards only" subset via the SQL layer.

## 5. Experimental matrix change

**Old matrix** (four configs, baseline-anchored):

1. Naive dense retrieval baseline
2. HyDE + semantic (–SQL ablation)
3. HyDE + SQL (–semantic ablation) — earlier proposed, dropped this weekend
4. Full three-stage cascade
5. Scryfall comparator

**New matrix** (three configs, outcome-anchored):

| # | Configuration | Role |
|---|---|---|
| 1 | Full cascade (HyDE + SQL + Nomic Embed v1.5) | Main result |
| 2 | –SQL ablation (HyDE + Nomic Embed v1.5, no pre-filter) | Isolates SQL pre-filter's contribution |
| 3 | Scryfall search with LLM-crafted expert queries | Best-case SQL-heavy comparator; doubles as implicit –HyDE evidence |

**Dropped configurations and rationale:**

- **Naive dense retrieval baseline** — no methodological need once the paper is outcome-anchored rather than diff-anchored. Reference numbers from raw semantic search still surface in Discussion via qualitative testing (see [`scripts/test_search.py`](../../scripts/test_search.py)), but not as a formal comparator.
- **–HyDE ablation (SQL + semantic without HyDE)** — evidence for HyDE's contribution comes from (a) the Scryfall comparator (Scryfall is a SQL-heavy no-HyDE system) and (b) argument-from-literature (Gao et al. 2022 established HyDE's contribution on standard benchmarks). Skipping this ablation is a scoping tradeoff; documented as a Limitations item in the eventual Discussion.
- **–semantic ablation (HyDE + SQL without vector search)** — a HyDE-to-SQL pipeline without semantic ranking would be a hobbled version of what Scryfall already does with purpose-built tuning. Scryfall (as comparator) tests the SQL-heavy paradigm more fairly. Skipping this saves complexity without losing meaningful signal.

## 8. Notes for final report

**Methodology section — Corpus preparation:**

> The Scryfall `oracle-cards` bulk-data dataset (2026-09-11 snapshot) contains 38,740 raw entries. Filtering rules exclude non-card layouts (tokens, emblems, art series, vanguard, planar, scheme), digital-only printings (Arena/MTGO exclusive), silver-bordered cards, memorabilia set-types, `funny` set-types (Un-set novelty products), and `token` set-types (token-booster products with normal-layout cards). The resulting corpus contains 31,972 face rows across 31,124 unique `oracle_id`s (80.3% retention rate); multi-face cards (transform, modal-DFC, split, adventure) are stored as separate rows keyed on `(oracle_id, face_index)`. Twenty-one card names remain with multiple `oracle_id`s in the final corpus, all legitimate variant printings from Universes Beyond crossovers and Strixhaven Mystical Archive style reprints; the SQL pre-filter offers `set` as a queryable attribute so users can opt into a subset if desired.

**Methodology section — Encoder choice:**

> Card ability text is encoded using `nomic-ai/nomic-embed-text-v1.5` (Nussbaum et al., 2024), a 137M-parameter bi-encoder in the sentence-transformer lineage (Reimers & Gurevych, 2019). Nomic Embed v1.5 requires task-specific prefixes (`search_document:` for documents, `search_query:` for queries), which we prepend at encode time. Embeddings are 768-dimensional and L2-normalized for cosine similarity retrieval. The encoder was selected during a September 2026 architectural pivot; a mid-2022 sentence-transformers model was originally used but replaced when the anchoring baseline evaluation was abandoned (see [redirect to Limitations / Methodology-history subsection]).

**Discussion section — Limitations:**

> A naive dense retrieval baseline was not run in this study. The design decision follows from framing the paper's central question as an outcome comparison against the domain-standard tool (Scryfall) rather than a diff comparison against an internal reference point; without a diff-based framing, the naive-baseline number does not carry methodological weight. Qualitative failure-mode observations from naive dense retrieval are documented in Section [X] via the `test_search.py` ad-hoc queries. Similarly, an ablation isolating HyDE's specific contribution (holding SQL and semantic stages fixed) was not run; evidence for HyDE's contribution comes from the Scryfall comparator (a SQL-heavy no-HyDE system) and from published results on standard IR benchmarks (Gao et al., 2022).
